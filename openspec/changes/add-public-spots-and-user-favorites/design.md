## Context

目前系統中景點相關的 API 端點都需要 JWT 認證，限制了未登入用戶瀏覽景點信息的能力。系統已有完整的認證授權機制（JWT + OAuth），但缺乏用戶個人收藏功能。景點數據採用軟刪除設計，且有管理員審查流程，需要確保公開訪問時不暴露敏感信息。

## Goals / Non-Goals

**Goals:**
- 將景點查詢類 API 改為公開訪問，提升用戶體驗和平台可發現性
- 實現用戶收藏景點功能，提升用戶粘性和參與度
- 保持數據安全性，確保敏感管理信息不對外公開
- 提供良好的前後端整合體驗

**Non-Goals:**
- 社交分享功能（收藏列表分享）
- 收藏分類與標籤系統
- 收藏統計分析與推薦算法
- 公開用戶收藏頁面（僅限個人查看）

## Decisions

### 資料庫設計

**新增 `user_favorites` 表：**
```sql
CREATE TABLE user_favorites (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  spot_id BIGINT NOT NULL REFERENCES spots(id) ON DELETE CASCADE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  UNIQUE(user_id, spot_id)
);

CREATE INDEX idx_user_favorites_user_id ON user_favorites(user_id);
CREATE INDEX idx_user_favorites_spot_id ON user_favorites(spot_id);
```

**設計決策理由：**
- 使用複合唯一索引 `(user_id, spot_id)` 防止重複收藏
- 級聯刪除確保數據一致性（用戶刪除或景點刪除時自動清理）
- 雙向索引支持高效查詢（用戶收藏列表 + 景點收藏計數）
- `created_at` 支持按時間排序功能

### API 權限調整

**景點查詢類端點（改為公開）：**
- `GET /api/spots` - 景點列表（分頁）
- `GET /api/spots/{id}` - 景點詳情
- `GET /api/spots/search` - 景點搜索

**新增收藏端點（需認證）：**
- `POST /api/favorites` - 添加收藏
- `DELETE /api/favorites/{spotId}` - 取消收藏  
- `GET /api/favorites` - 個人收藏列表
- `GET /api/favorites/check/{spotId}` - 檢查收藏狀態

**設計決策理由：**
- 分離查詢與操作權限，符合 RESTful 設計原則
- 收藏功能作為獨立資源，便於未來擴展
- 檢查端點支持前端按需查詢收藏狀態

### 前端狀態管理

**未登入狀態：**
- 可瀏覽景點列表、詳情、搜索
- 收藏按鈕隱藏或顯示為"登入後收藏"

**登入狀態：**
- 顯示收藏按鈕當前狀態（已收藏/未收藏）
- 可訪問個人收藏列表頁面
- 支持快捷收藏/取消收藏操作

**設計決策理由：**
- 漸進式增強體驗，不強制登入
- 登入前後狀態平滑過渡
- 收藏狀態與認證狀態同步

### 數據安全策略

**公開景點數據過濾：**
- 自動過濾 `deleted_at IS NOT NULL` 的景點
- 僅返回已審查通過的景點（如需審查狀態）
- 隱藏管理標記和內部審查信息

**設計決策理由：**
- 防止數據洩露，保護用戶隱私
- 確保公開數據質量，避免展示未審查內容
- 符合系統現有的軟刪除策略

### 級聯刪除處理

**數據庫級別：**
- `user_favorites` 表設置 `ON DELETE CASCADE`
- 用戶刪除時自動清理其所有收藏記錄
- 景點刪除時自動清理相關收藏記錄

**業務邏輯補充：**
- 景點軟刪除時保留收藏記錄（但前端不顯示）
- 提供管理員手動清理過期收藏的選項

**設計決策理由：**
- 利用資料庫約束確保引用完整性
- 減少應用層級聯刪除邏輯複雜度
- 平衡數據保留與清理需求

## Risks / Trade-offs

### 性能風險

**風險：** 公開訪問可能導致景點查詢量大幅增加，影響系統性能

**緩解措施：**
- 保持現有的分頁限制（pageSize 上限 100）
- 考慮添加 API 限流機制
- 優化資料庫查詢索引

### 數據一致性風險

**風險：** 前端收藏狀態與後端不同步，用戶體驗混亂

**緩解措施：**
- 收藏操作後立即更新前端狀態（樂觀更新）
- 提供檢查端點支持按需同步
- 錯誤時回滾前端狀態並提示用戶

### 遷移複雜性風險

**風險：** 權限調整可能影響現有用戶的依賴行為

**緩解措施：**
- 保持現有認證機制不變，僅移除查詢端點的 `[Authorize]`
- 提供充足的測試覆蓋確保權限正確
- 前端保持認證流程，用戶可選擇登入獲得完整功能

### 存儲成本風險

**風險：** 收藏記錄無限增長，佔用資料庫空間

**緩解措施：**
- 監控收藏記錄增長趨勢
- 考慮未來添加收藏上限或自動清理策略
- 定期備份重要收藏數據

## Migration Plan

1. **資料庫遷移：**
   - 執行 Flyway migration 創建 `user_favorites` 表
   - 添加必要的索引和約束

2. **後端 API 調整：**
   - 移除景點查詢端點的 `[Authorize]` 標記
   - 實現收藏相關的 Controller 和 Service
   - 更新 OpenAPI 文檔

3. **前端適配：**
   - 調整認證守衛，允許未登入訪問景點頁面
   - 實現收藏 UI 組件和狀態管理
   - 處理登入前後狀態同步

4. **測試驗證：**
   - 單元測試：收藏 CRUD 操作
   - 集成測試：權限控制正確性
   - E2E 測試：用戶流程完整驗證

5. **部署策略：**
   - 採用滾動更新，確保向後相容
   - 監控錯誤日誌和性能指標
   - 準備快速回滾方案

## Open Questions

1. **收藏上限：** 是否需要限制單個用戶的收藏數量？（目前不設限）
2. **批量操作：** 是否需要支持批量收藏/取消收藏功能？（本期僅支持單個操作）
3. **收藏計數：** 是否需要在景點列表中顯示收藏計數？（可作為後續優化）
4. **離線支持：** 是否需要支持離線收藏狀態？（本期僅在線狀態）
